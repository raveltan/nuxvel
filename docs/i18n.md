# Internationalization

## Introduction

Every nuxvel app has [`nuxt-i18n-micro`](https://s00d.github.io/nuxt-i18n-micro/). You do not install it. The module adds it with one locale, English (`en`). An app with one locale has no route prefix, no extra route and no extra meta tag. To show the app in more languages, add locales and their translation files.

An app from [`create-nuxvel`](./create.md) has two locales, English (`en`) and Chinese (`zh`). Its pages, layouts and components use `$t`. To keep only English, see [Keeping only English](#keeping-only-english).

## Configuration

Configure the library with the `i18n` key of `nuxt.config.ts`. The examples use English and Chinese:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ["@nuxvel/nuxt"],
  i18n: {
    locales: [
      { code: "en", iso: "en-US" },
      { code: "zh", iso: "zh-CN" },
    ],
  },
});
```

nuxvel sets these defaults. Each option of the `i18n` key overrides the default of the same name.

| Option | Default | Value |
|---|---|---|
| `locales` | `[{ code: "en", iso: "en-US" }]` | The locales of the app. nuxvel adds the default only when the app sets no `locales`. |
| `defaultLocale` | `"en"` | The locale of a path with no prefix. |
| `strategy` | `"prefix_except_default"` | The default locale has no prefix: `/posts` is English and `/zh/posts` is Chinese. |
| `translationDir` | `"locales"` | The folder of the translation files, in the root of the app. |
| `fallbackLocale` | The `defaultLocale` | A key that the file of a locale does not have shows the text of this locale. See [Missing translations](#missing-translations). |
| `localeCookie` | `"user-locale"` | The cookie that keeps the locale the user chose. |
| `meta` | `true` with `nuxvel.seo` and two or more locales, else `false` | The library adds `<html lang>`, the canonical link, `og:url`, `og:locale` and the `hreflang` links. See [SEO and the sitemap](#seo-and-the-sitemap). |
| `disableWatcher` | `true` | A build does not write empty page files into `locales/`. |
| `translationPayloads.mode` | `"source"` | The server merges the global file and the page file of a locale on each request, and keeps the result in memory. A page with no page file gets the global translations. |

A page behind the `auth` middleware stays private in each locale: `/zh/profile` has the same route rules as `/profile`. With `nuxvel.seo`, the sitemap leaves out both.

## Translation files

A global file holds the translations that each page can use. It has the name of the locale:

```text
locales/
  en.json
  zh.json
```

```json
{
  "greeting": "Hello",
  "nav": { "posts": "Posts" }
}
```

A page file holds the translations of one page. Its folder has the name of the route, for example `posts-id-edit` for `app/pages/posts/[id]/edit.vue`. A key in a page file overrides the same key in the global file.

```text
locales/
  pages/
    posts/
      en.json
      zh.json
```

A layer can have its own `locales/` folder. The library merges the files of each layer with the files of the app.

### Missing translations

A key that `locales/zh.json` does not have shows the text of the default locale, for example the English text. The server does the same for [mail](#mail) and [validation messages](#validation-messages). Only a key that the default locale does not have either shows the key itself, with a warning in the browser console in development.

[`nuxvel test:arch`](./cli.md#nuxvel-testarch) fails before a translation goes missing:

```text
✖ locales/zh.json: missing home.intro, which locales/en.json has
✖ layers/billing/locales/zh.json: missing, translate layers/billing/locales/en.json into it
✖ common.save has a different text in locales/en.json and layers/billing/locales/en.json, give each meaning its own key
✖ app/pages/index.vue: "home.titel" is in no en.json, add it to the translation file of the default locale
```

- Each translation file of the default locale, global or for a page, has a file for each other locale, with each of its keys.
- Two layers do not give the same key different texts. The first layer would win, and the text of the other layer would never show.
- Each literal key of `$t`, `$ts`, `t`, `ts` and `<i18n-t keypath>` in `app/` is in a file of the default locale. A key built at runtime, such as `` $t(`status.${state}`) ``, is not checked.

Name a key after the place and the meaning of the text, not after its English words. "Close" a dialog and "Close" an account are `dialog.close` and `account.close`, so each language can translate them differently.

## Translating a page

`$t` gives the text of a key in the current locale. Use a dot for a nested key:

```vue
<template>
  <h1>{{ $t("greeting") }}</h1>
  <p>{{ $t("nav.posts") }}</p>
</template>
```

`$t` can return a value that is not a string, for example an object for a key that has nested keys. A prop that needs a string, for example `label` of `<UButton>`, uses `$ts`. `$ts` always returns a string:

```vue
<template>
  <UButton :label="$ts('nav.posts')" />
</template>
```

In a script, `useI18n()` gives the same helpers without the `$`:

```vue
<script setup lang="ts">
const { ts } = useI18n();

useHead({ title: () => ts("greeting") });
</script>
```

`<i18n-t>` puts markup into a translation. A slot with the name of a placeholder replaces the placeholder:

```vue
<template>
  <!-- en.json: "sentTo": "A link went to {email}." -->
  <i18n-t keypath="sentTo" tag="p">
    <template #email><strong>{{ email }}</strong></template>
  </i18n-t>
</template>
```

## Links and the locale switcher

A link with a route name, for example `:to="{ name: 'posts' }"`, always opens the page in the default locale. `$localeRoute()` gives the route of a page in the current locale. On a `/zh/...` page, `$localeRoute({ name: 'posts' })` goes to `/zh/posts`. Use it in the `to` of `<NuxtLink>`, `<ULink>` and `<UButton>`, so the link keeps the locale and the route name:

```vue
<template>
  <ULink :to="$localeRoute({ name: 'posts' })">{{ $t("nav.posts") }}</ULink>
</template>
```

In a script, `localeRoute()` of `useI18n()` does the same: `navigateTo(localeRoute({ name: "posts" }))`.

`<i18n-link>` also links to a page in the current locale. On a `/zh/...` page, `to="/posts"` goes to `/zh/posts`:

```vue
<template>
  <i18n-link to="/posts">{{ $t("nav.posts") }}</i18n-link>
</template>
```

`<i18n-switcher>` shows a menu of the locales. It opens the same page in the locale that the user selects, and sets the `user-locale` cookie:

```vue
<template>
  <i18n-switcher />
</template>
```

The app from `create-nuxvel` has its own switcher, `app/components/LocaleSwitcher.vue`, built with `<USelect>`. Each layout shows it. It shows the `displayName` of each locale in `i18n.locales`. It calls `switchLocale()` of `useI18n()`, and for a signed-in user also `authClient.updateUser({ locale })`, so the [auth mails](#the-locale-of-the-user) follow the choice. With one locale, the switcher shows nothing.

## Cached pages

The library redirects `/` to the locale of the visitor. The `user-locale` cookie and the `Accept-Language` header give that locale. For example, a visitor with `user-locale=zh` goes from `/` to `/zh`. The library also sets the `user-locale` cookie on each `/zh/...` page.

A [`cached`](./rendering.md#rendering-presets) page is one copy for all visitors, so it gives the same answer to each visitor:

- The server renders the copy without the cookies and the `Accept-Language` header of the visitor. A cached `/` thus never redirects. Each visitor gets the page in the default locale and selects another locale with the switcher.
- The copy sets no cookie. A cached `/zh/...` page does not set the `user-locale` cookie. See [Rendering: cached pages and cookies](./rendering.md#cached-pages-and-cookies).

A page that is not cached keeps the redirect and the cookie.

## Nuxt UI and dates

`useUiLocale()` gives the Nuxt UI locale of the current i18n locale. Give it to `<UApp>` in `app.vue`. Then the labels of the Nuxt UI components, for example the close button of `<UAlert>`, are in the language of the page:

```vue
<!-- app/app.vue -->
<script setup lang="ts">
const uiLocale = useUiLocale();
</script>

<template>
  <UApp :locale="uiLocale">
    <NuxtPage />
  </UApp>
</template>
```

nuxvel finds the Nuxt UI locale from the `iso` of each locale in `i18n.locales`: `zh-CN` gives `zh_cn`. If Nuxt UI has no locale for the full `iso`, nuxvel uses the language: `de-DE` gives `de`. If Nuxt UI has no locale for the language, the locale gets `en`. The browser bundle contains only the Nuxt UI locales of `i18n.locales`. With `nuxvel: { ui: false }`, `useUiLocale()` is not auto-imported.

[`<DateTime>`](./rendering.md#dates) formats a date in the `iso` of the current locale. On `/zh/posts`, `<DateTime :value="post.createdAt" :options="{ dateStyle: 'long' }" />` shows `2026年1月2日`. The `locale` prop overrides the locale.

## The nuxvel components

The nuxvel components have English and Chinese text: `<AuthForm>`, `<SocialSignIn>`, `<NotificationBell>`, `<PushToggle>`, `<PwaInstallPrompt>`, `<MaintenanceBanner>`, `<Maintenance>`, `<QueryState>`, `<DataTable>` (its sort buttons and filters), `<SearchInput>`, `<UploadField>` and the errors of `useUpload()`, `<PresenceAvatars>`, `<TypingIndicator>`, the dialog of `useConfirm()`, the unsaved changes prompt of `useActionForm()`, the submit button of `<ActionForm>` and the `/offline` page. They show the text of the page locale. A label that you pass, such as the `confirmLabel` of `useConfirm()`, replaces the nuxvel text. `<AuthForm>`, `<SocialSignIn>` and the `auth` and `guest` middleware keep the locale of the page when they open another page: a sign-in on `/zh/sign-in` opens `/zh`.

The labels of the fields of `<ActionForm>` come from keys of the app, `<action path>.fields.<name>`, such as `post.create.fields.title`. See [Forms](./frontend.md#the-form-from-the-schema).

The keys start with `nuxvel.`, for example `nuxvel.authForm.signIn`. To change a text, put its key in a translation file of the app. A key of the app overrides the same key of nuxvel. The other keys keep the nuxvel text:

```json
{
  "nuxvel": {
    "authForm": { "signIn": "Log in" }
  }
}
```

The keys and the English text are in `node_modules/@nuxvel/nuxt/dist/runtime/locales/en.json`. For a locale other than `en` and `zh`, nuxvel uses the text of the language of the locale, for example `zh` for `zh-TW`. If nuxvel has no text for the language, the components show the English text. To translate the text, put the `nuxvel` keys in the file of the locale, for example `locales/fr.json`. Each key that the file does not have keeps the English text.

At each build, nuxvel writes one file for each locale of `i18n.locales` into `.nuxt/nuxvel-locales/`. It gives that folder to `nuxt-i18n-micro` with the `additionalTranslationDirs` option. The library merges the folder before the `locales/` files of the app.

## Storybook

A component that uses `$t` renders in Storybook with the translation files of the app. The **Locale** menu of the toolbar selects the locale of all stories. The `locale` parameter selects the locale of one story:

```ts
export const Chinese: Story = { parameters: { locale: "zh" } };
```

See [Storybook: Locale](./storybook.md#locale).

## Mail

A mail renders in one locale. `$mails.x.send()` and `sendMailNow()` take a `locale` option. Without it, the mail renders in the locale that `currentLocale()` returns. The template translates with `$t`, and the `subject` with `t`, from the global translation files:

```ts
await $mails.welcome.send({ to: user.email, name: user.name }, { locale: "zh" });
```

The nuxvel auth mails have English and Chinese text. To change a text, put its key in a translation file of the app. See [Mail: Mail in a locale](./mail.md#mail-in-a-locale).

The auth mails and the notification mails go out in the locale of the user. See [The locale of the user](#the-locale-of-the-user).

## The locale of the user

The `user` table has a `locale` column. Sign-up sets it to `currentLocale()`. `authClient` sends the locale of the page, so a sign-up on `/zh` gives the user `zh`. A locale switcher can also save the choice of a signed-in user:

```ts
await authClient.updateUser({ locale: "zh" });
```

The server accepts only a locale code from `i18n.locales`. The links in the auth mails go to the pages of the user's locale, for example `/zh/reset-password`. See [Auth: the locale of the user](./auth.md#the-locale-of-the-user).

## SEO and the sitemap

With [`nuxvel.seo`](./seo.md) and two or more locales, each page gets the tags of its locale. For `/zh/posts`, the page renders:

```html
<html lang="zh-CN" dir="auto">
<link rel="canonical" href="https://blog.example.com/zh/posts">
<link rel="alternate" href="https://blog.example.com/posts" hreflang="en-US">
<link rel="alternate" href="https://blog.example.com/zh/posts" hreflang="zh-CN">
<link rel="alternate" href="https://blog.example.com/posts" hreflang="x-default">
<meta property="og:url" content="https://blog.example.com/zh/posts">
<meta property="og:locale" content="zh_CN">
<meta property="og:locale:alternate" content="en_US">
```

The `iso` of a locale gives `lang` and `hreflang`. The `x-default` link goes to the page in the default locale. The page has one canonical link and one `og:url`.

The sitemap has one sitemap for each locale. `/sitemap.xml` redirects to `/sitemap_index.xml`, which lists `/__sitemap__/en-US.xml` and `/__sitemap__/zh-CN.xml`. `robots.txt` points to `/sitemap_index.xml`. Each URL in the sitemap lists the same page in each locale.

An app with one locale keeps one `/sitemap.xml` and gets no `hreflang` link and no `og:locale`.

## The locale on the server

`currentLocale()` returns the locale code of the current request, for example `"zh"`. It is auto-imported in `server/`. It uses the first locale that it finds in this order:

1. The route prefix, for example `zh` in `/zh/posts`.
2. The `user-locale` cookie.
3. The `Accept-Language` header.
4. The default locale.

A tRPC call from a page sends the locale of that page in the `x-nuxvel-locale` header. Thus a procedure gets the locale of the page that calls it, also during the server render. The header comes before the other sources.

A procedure gets the same value in `ctx.locale`. An action gets it in the second argument of its handler:

```ts
// server/actions/posts/create-post.action.ts
export const createPostAction = defineAction({
  input: createPostInput,
  async handler(input, { actor, locale }) {
    // ...
  },
});
```

A caller can give an action a locale: `createPostAction(input, { actor, locale: "zh" })`. In that action, and in each action that it calls, `currentLocale()` returns that locale. A job, a schedule and a command have no request. There, `currentLocale()` returns the default locale, unless the code runs in an action that has a locale.

In a test, give the locale to the test client. `api`, `fetch` and `$fetch` then send it as the locale of the page:

```ts
const { api } = actingAs(await userFactory(), { locale: "zh" });
const posts = await guest({ locale: "zh" }).api.post.list();
const page = await visit("/posts", { locale: "zh" });
```

`visit` with `locale` opens the page in that locale, here `/zh/posts`. See [Testing: acting as a user](./testing.md#acting-as-a-user) and [Testing: visit](./testing.md#visit).

## Validation messages

The Zod messages of an action and of a tRPC procedure's `.input()` are in the locale of the call. The server does not change the global Zod configuration. It gives the messages of the locale to each parse:

```ts
const { api } = guest({ locale: "zh" });

await expect(api.post.create({ title: "" })).rejects.toHaveValidationErrors({
  title: "数值过小：期望 string >=1 字符",
});
```

In the browser, a form that validates with a schema, for example `<UForm :schema>`, shows the messages of the current page locale.

nuxvel finds the [Zod locale](https://zod.dev/error-customization#internationalization) from the `iso` of each locale in `i18n.locales`: `zh-CN` gives `zhCN`. If Zod has no locale for the full `iso`, nuxvel uses the language: `de-DE` gives `de`. If Zod has no locale for the language, the locale gets English. The browser bundle contains only the Zod locales of `i18n.locales`. An app that has only English locales gets no extra code. A `message` or an `error` that you set on a schema overrides the message of the locale.

## Keeping only English

An app with only English needs no change. If the app has more locales, do these steps to keep only English:

1. Remove the other locales from `i18n.locales` in `nuxt.config.ts`.
2. Delete the translation files of the other locales, for example `locales/zh.json`.

In an app from `create-nuxvel`, these are the two steps: remove `zh` from `i18n.locales` and delete `locales/zh.json`. The pages keep `$t` with the English text of `locales/en.json`. `LocaleSwitcher` shows nothing with one locale. If you added `<i18n-switcher>` to a layout, remove it.
