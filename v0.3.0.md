# nuxvel 0.3.0 — plan

Goal: an app written with nuxvel reads like the feature it implements, not
like the glue between Pinia Colada, tRPC, Drizzle and Better Auth. Every
convenience has an escape hatch down to the library underneath, so nothing
here takes control away from the app.

This is a minor release under `0.x`, so it may break apps. Each breaking
change has exact upgrade steps in `CHANGELOG.md` **and** a codemod in
`nuxvel upgrade` (milestone 0), so an existing app reaches 0.3.0 with
`npm update` + one command.

Decisions taken (from the planning questions):

| Topic | Decision |
|---|---|
| Version | 0.3.0, breaking changes allowed, superseded APIs are removed |
| App-side tRPC global | `$api` |
| `$api.x.useQuery()` result | Pinia Colada's own return wrapped in `reactive()` |
| Invalidation | server-declared (`invalidates` on the action) drives the client cache; fallback to the mutation's namespace; `invalidate` overrides |
| Actions as procedures | both: `procedure:` on `defineAction` and `.action()` on routers |
| Omitted `authorize` | signed-in users only; `public: true` opts out |
| Forms | full ladder: `<ActionForm>` + `<ActionField>` generated from the schema |
| Imports | aliases + lint; no bare table globals |
| Extras | route groups, `belongsTo()`, auth composables |

---

## Principles (the rules every milestone follows)

1. **Three ways to reach a name, one per kind.**
   - *Bare globals* are framework verbs only: `define*`, `use*` and a closed
     list (`can`, `authorize`, `paginate`, `audit`, ...). No app-defined name
     ever becomes a bare global.
   - *`$kind` namespaces* hold what the app defines in discovered folders:
     `$api`, `$actions`, `$jobs`, `$channels`, `$policies`, `$mails`, ...
   - *One alias import* for everything else: `#nuxvel/schema`,
     `#nuxvel/factories`, `#server/*`, `#shared/*`. Never `../`.
2. **Thin pass-through, not a parallel API.** Every option bag nuxvel adds
   passes the underlying library's options straight through (Pinia Colada,
   Nuxt UI, Drizzle, Better Auth). nuxvel only adds its own keys. This is
   the lesson of tRPC v11 moving from wrapper hooks to option factories.
3. **Customization ladder.** Every high-level API documents the step below
   it: component → props → slot → layout → app config → composable → raw
   library. Going down one step keeps the automatic behaviour of the rest.
4. **Discovery replaces registration** (existing rule) — now also for
   procedures that only forward to an action.
5. **The server knows; the client doesn't guess.** What a mutation changes,
   which field a failure belongs to, what a user may do — declared once on
   the server, carried to the client in types or in the response.

## Milestone 0 — `nuxvel upgrade` codemods

Ship first, so every later breaking commit adds its codemod in the same
commit (CLAUDE.md: every release must reach existing apps).

- `nuxvel upgrade` runs every codemod for versions newer than the one in
  `package-lock.json`; `--dry-run` prints the diff; `--only <name>` runs one.
- Built on `ts-morph` or `magicast` (whichever the CLI already pulls in) for
  `.ts`, and `@vue/compiler-sfc` for the `<script>` block of `.vue` files.
- A codemod that cannot rewrite a call safely leaves it and prints the
  file and line with the manual step.
- Tests: one `packages/cli/test/upgrade.test.ts` suite per codemod, on a
  `scratchPlayground()` seeded with the old code.
- Docs: `docs/cli.md#upgrade`, and `CHANGELOG.md` names the command at the
  top of the 0.3.0 entry.

## Milestone 1 — Imports: aliases and the lint rule

**Problem.** Docs, playground and tutorials hold ~533 relative imports
(`../../database/schema/posts.schema`), though `#nuxvel/schema` is already
the documented way. Some files import schemas that are auto-imported anyway.

**Before**
```ts
import { createPostAction } from "../../actions/posts/create-post.action";
import { userTable } from "../../database/schema/auth.schema";
import { postsTable } from "../../database/schema/posts.schema";
import { postPolicy } from "../../policies/post.policy";
import { createPostInput, postIdInput, postSchema, updatePostInput } from "../../../shared/schemas/post";
```
**After**
```ts
import { postsTable, userTable } from "#nuxvel/schema";
// actions → $actions, policies → $policies, shared/schemas → auto-imported
```

Work:
1. Verify `#server/*` and `#shared/*` resolve in nuxvel's Nitro build, in
   `nuxt typecheck` of a linked starter, and in the CLI's built server.
   Fix the alias registration if not (double registration rule in
   CLAUDE.md applies to generated modules only; these are Nuxt's own).
2. `#nuxvel/factories` exports every factory for tests (exists: confirm it
   is importable from `tests/` of an app, add if not).
3. ESLint rule `nuxvel/no-parent-imports` in the `architecture` preset of
   `@nuxvel/nuxt/eslint`, reported by `nuxvel test:arch`: an import that
   climbs out of its folder (`../`) into another kind folder is an error,
   with a fix to the alias. Sibling imports inside one folder stay legal.
   Also flags an import of a name that is auto-imported from
   `shared/schemas/`.
4. Codemod `imports`: rewrite to the aliases.
5. Rewrite docs, tutorials, playground and template.

Customizable: the rule's allowed patterns are options of the ESLint rule;
an app can turn it off in its `eslint.config`.

Breaking: an app whose CI runs `test:arch` gets new errors → codemod
`imports` fixes them.

## Milestone 2 — `$api` and procedure composables (app)

**Before** (`docs/tutorials/invoices.md`, MemberList)
```ts
const trpc = useTRPC();
const queryCache = useQueryCache();
const members = useQuery(trpc.team.members.queryOptions({ id: props.teamId }));
const { data: abilities } = useQuery(trpc.team.abilities.queryOptions({ id: props.teamId }));
const refresh = () => queryCache.invalidateQueries({ key: trpc.team.members.key() });
const { mutate: changeRole, error: roleError } = useMutation({
  ...trpc.team.changeRole.mutationOptions(),
  onSettled: refresh,
});
```
**After**
```ts
const members = $api.team.members.useQuery(() => ({ id: props.teamId }));
const changeRole = $api.team.changeRole.useMutation();
```
```vue
<UAlert v-if="changeRole.error" :title="changeRole.error.message" />
<USelect @update:model-value="changeRole.mutate({ membershipId: m.id, role: $event })" />
```

API:
- `$api` — auto-imported app namespace. Resolves `useNuxtApp().$trpc`
  lazily at call time, so it follows the same "call inside setup, a plugin
  or middleware" rule as any composable. Also available in templates.
  Replaces `useTRPC()`.
- On a query procedure:
  - `.useQuery(input | () => input, options?)` → `reactive(useQuery(...))`.
    `options` is Pinia Colada's `UseQueryOptions` minus `key`/`query`
    (passed through: `enabled`, `staleTime`, `placeholderData`, ...).
  - `.queryOptions(input)` and `.key(input?)` stay (low level).
- On a mutation procedure:
  - `.useMutation(options?)` → `reactive(useMutation(...))`. `options` is
    Pinia Colada's `UseMutationOptions` minus `mutation`, plus nuxvel's
    `invalidate`, `toast`, `optimistic` (milestones 3, 4).
  - `.mutationOptions(options?)` stays (low level), and accepts the same
    nuxvel keys.
- On a namespace: `.key()` stays.
- `<QueryState :query>` accepts both the reactive and the ref shape.
- Reserved names on the proxy grow by `useQuery`, `useMutation`; the
  existing compile-time `ReservedNameCheck` covers them.

Customizable: every Pinia Colada option passes through; `queryOptions()`
with Colada's own `useQuery` remains the escape hatch, documented as such.

Breaking: `useTRPC()` removed → codemod `use-trpc` rewrites
`const trpc = useTRPC()` to uses of `$api`, and `useQuery(trpc.x.queryOptions(i))`
to `$api.x.useQuery(i)` where the shape matches.

Type proof: a probe `_api-type-check.vue` asserting `$api.post.byId.useQuery()`
data is not `any` and needs no `.value` in the template.

Docs: `frontend.md`, `api.md`, every tutorial.

## Milestone 3 — Server-declared invalidation

**Before**
```ts
// action
invalidates: ["posts:*"],
// client
onSuccess: async () => { await queryCache.invalidateQueries({ key: trpc.post.key() }); }
```
**After**
```ts
// action
invalidates: ["posts"],
// client: nothing
```

Design:
- An action's `invalidates` becomes a list of tags, written as key arrays
  or the existing string form (`"posts"`, `["posts", { id }]`). The server
  cache (`remember(...)` / `cacheForget`) and the client query cache use
  the same tags.
- tRPC mutation responses carry the tags the call invalidated (response
  meta via the existing link chain, not the payload). The client link
  invalidates every query whose key starts with `["trpc", ...tag]` after
  the mutation settles.
- An action without `invalidates`: the client invalidates the mutation's
  own router namespace (`team.changeRole` → `["trpc", "team"]`).
- `remember()` accepts a key array: `remember(["posts", "list", input], ...)`.

Customizable:
- `invalidate:` on `.useMutation()` / `useActionForm` / `.mutationOptions()`
  replaces the server's list for that call; `invalidate: false` turns it off;
  `invalidate: (result, input) => [...]` computes it.
- `nuxvel.api.invalidateFallback: "namespace" | false` in `nuxt.config.ts`.

Breaking: a client that invalidated by hand still works (double refetch is
deduped by Colada). Codemod `invalidate` removes the obvious
`onSuccess/onSettled: () => queryCache.invalidateQueries({ key: trpc.x.key() })`.

Tests: functional test that a mutation's response carries the tags; story
test that the list query refetches after the mutation (trpcSpy).

Docs: `cache.md`, `actions.md`, `frontend.md`.

## Milestone 4 — Mutation options instead of wrapper functions

**Before**
```ts
useMutation(optimistic(toasted(trpc.post.delete.mutationOptions(), "Post deleted"), {
  key: () => trpc.post.list.key(input.value),
  apply: (list, { id }) => ({ ...list, rows: list.rows.filter((r) => r.id !== id) }),
}));
```
**After**
```ts
$api.post.delete.useMutation({
  toast: "Post deleted",
  optimistic: { key: () => $api.post.list.key(input.value), apply: removeRow() },
  confirm: (post) => ({ title: "Delete post?", description: `"${post.title}" will be deleted.`, color: "error" }),
});
```

- `toast: string | (result) => string | ToastProps` — Nuxt UI toast props
  pass through.
- `optimistic: { key, apply }` — same semantics as `optimistic()` today.
- `confirm: ConfirmOptions | (input) => ConfirmOptions` — runs `useConfirm()`
  before the mutation; a cancel resolves without calling.
- List patch helpers for `paginated()` data, usable in `optimistic.apply`
  and `useLiveQuery` `on`: `removeRow(match?)`, `prependRow({ when? })`,
  `replaceRow(match?)`. They keep `total`/`perPage` right and skip
  duplicates.

Customizable: each key also accepts a function; Pinia Colada `onMutate`,
`onError`, `onSettled` still pass through and run after nuxvel's.

Breaking: `toasted()` and `optimistic()` removed → codemod `mutation-options`.

Docs: `frontend.md#optimistic-updates`, `#toasts`, `#confirm`.

## Milestone 5 — Actions as procedures

**Before**
```ts
update: authedProcedure
  .input(updatePostInput)
  .output(postOutputSchema)
  .use(audited("post.updated", { target: postsTable }))
  .mutation(({ input, ctx }) => updatePostAction(input, { actor: ctx.actor })),
```
**After** — either in the action:
```ts
export const updatePostAction = defineAction({
  input: updatePostInput,
  procedure: "authed",
  audit: "post.updated",
  handler: ...
});
```
or in a router, when the procedure needs its own middleware or OpenAPI:
```ts
update: authedProcedure.openapi({ path: "/posts/{id}" }).action($actions.posts.updatePost),
```

- `procedure: "public" | "authed" | "admin" | Procedure` — the action is
  mounted at its path (`posts.updatePost` from
  `server/actions/posts/update-post.action.ts`), typed on `$api`. A
  procedure builder value allows a custom one (`roleProcedure("editor")`).
- `.action(a)` on every procedure builder: input from the action, output
  optional, errors carried.
- A router key and an auto-mounted action at the same path fail the build
  with both file names.
- The actor is ambient in procedures; docs drop `{ actor: ctx.actor }`
  (61 places) — no code change needed.
- `audit: "post.updated"` on `defineAction` (target inferred from the
  returned row, or `audit: { name, target }`).
- `.openapi({ path?, summary?, tags?, protect? })` — method from
  query/mutation, tags from the router, path params from the input.

Customizable: any action can stay internal (no `procedure`); `.action()`
composes with any `.use()`; `.meta({ openapi })` keeps working underneath.

Breaking: `audited()` middleware removed → codemod `audit` moves it to the
action's `audit` option (or to `audit()` inside the handler when the
procedure has no action).

Docs: `actions.md`, `api.md`, `openapi.md`, `audit.md`.

## Milestone 6 — Forms: `useActionForm` upgrades

**Before**
```ts
const form = useActionForm(addMemberInput, toasted(trpc.team.addMember.mutationOptions(), "Member added"), {
  defaults: { teamId: props.teamId, email: "", role: "member" },
  failures: { "team.unknown-email": "email" },
  onSuccess: refresh,
});
```
**After**
```ts
const form = useActionForm($api.team.addMember, {
  defaults: { teamId: props.teamId },
  toast: "Member added",
});
```

- First argument: a mutation procedure from `$api`. The input schema comes
  from a generated registry `#nuxvel/procedure-inputs` (path → schema
  import from `shared/schemas/`). A procedure whose schema is not in
  `shared/` fails to compile with a message to move it, or to pass the
  schema explicitly: `useActionForm($api.x, { schema })`.
- `defaults` is partial: missing keys start `undefined`; the schema's own
  `.default()` fills the rest; `defaults: props.post` picks only the
  schema's keys.
- Failure → field mapping on the server:
  `errors: { "unknown-email": { message: "...", field: "email" } }`
  (string form stays). `failures` on the client remains as an override.
- `invalidate`, `toast`, `confirm` from milestones 3–4.

Breaking: the `(schema, mutationOptions, options)` signature is removed →
codemod `action-form`.

## Milestone 7 — Forms: `<ActionForm>` and `<ActionField>`

The customization ladder, each step keeping validation, server errors,
focus, toast, invalidation and the unsaved-changes guard:

1. `<ActionForm :action="$api.team.addMember" :defaults="{ teamId }" />`
   — every field generated from the schema.
2. Props: `:fields="{ email: { label, placeholder, hint } }"`,
   `submit-label`, `hidden="teamId"`, `class`, `:ui` (Nuxt UI style).
3. One field: `<template #field-role="{ field }">...</template>`.
4. Layout: default slot with `<ActionField name="street" />` anywhere,
   `#actions="{ pending }"` for buttons.
5. App-wide: `app.config.ts` `ui.actionForm` slots, and
   `nuxvel.form.inputs: { date: MyDatePicker, money: MoneyInput }`.
   Per field in the shared schema: `z.string().meta({ input: "textarea" })`.
6. `const form = useActionForm(...)` with your own `<UForm>`.

Schema → input map (defaults): string → `UInput`, email/url → typed
`UInput`, enum → `USelect`, boolean → `USwitch`, number → `UInputNumber`,
date → `UInputDate`, `richText()` → the rich text editor, an upload key →
`<UploadField>`. Arrays of objects and unions have no default: a
dev-only warning names the field and asks for a slot.

Labels: i18n key `<action path>.fields.<name>`, fallback humanized name.

Storybook: `<ActionForm>` stories render from `mockTrpc`; a `play`
function can submit and assert field errors.

`AuthForm.vue` is rebuilt on `<ActionForm>` (internal, proves the ladder).

Docs: `frontend.md#forms` (new page section per ladder step), `storybook.md`.

## Milestone 8 — Server helpers

**Load + authorize**
```ts
// before
const post = await findOrFail(postsTable, input.id);
await authorize(ctx.actor, "update", postsTable, post);
// after
const post = await findAuthorized(postsTable, input.id, "update");
```
- `findAuthorized(table, id, ability)`; `can()`/`authorize()` drop the
  actor argument (ambient actor). The actor-first signature is removed →
  codemod `actor-arg`.

**Single-row writes**
```ts
// before
const updated = await useDb().update(postsTable).set({ title }).where(eq(postsTable.id, id)).returning().then(firstOrFail);
// after
const updated = await updateOne(postsTable, id, { title });
const post = await insertOne(postsTable, { title, body, authorId });
```
Thin over Drizzle; the Drizzle chain stays for anything else.

**Abilities in the output**
```ts
byId: publicProcedure.input(postIdInput).output(withAbilities(postSchema, ["update", "delete"]))
  .query(({ input }) => findOrFail(postsTable, input.id)),
```
Adds `can: { update, delete }` to each row (batched through `canMany` and
the policy's `preload`). Client: `post.can.update`. Replaces separate
`abilities` procedures (docs and playground lose them).

**Definitions with methods; after-commit by default**
```ts
// before
await dispatchAfterCommit("post.notify-followers", { postId: post.id });
await broadcastAfterCommit("posts", "created", post);
// after
await $jobs.post.notifyFollowers.dispatch({ postId: post.id });
await $channels.posts.broadcast("created", post);
```
Inside a transaction they wait for the commit; outside they run now.
Options (`delay`, `priority`, `dispatcher`, `params`) unchanged.
Breaking: `dispatchAfterCommit`, `broadcastAfterCommit` and the string-name
forms removed → codemod `definition-methods`.

**Smaller**
- `useLogger()` takes its tag from the running action/job.
- `audit(name, row)` is the documented form.
- `defineSeeder` may return lines that `db:seed` prints.

Docs: `database.md`, `authorization.md`, `queues.md`, `realtime.md`.

## Milestone 9 — Schema: `belongsTo()`

```ts
// before
authorId: text("author_id").notNull().references(() => userTable.id, { onDelete: "cascade" }),
(table) => [index("posts_author_id_idx").on(table.authorId), searchIndex(table)],
export const postFactory = defineFactory(postsTable, { authorId: async () => (await userFactory()).id });
await postFactory.for("authorId", demo)(post);
// after
authorId: belongsTo(userTable),
(table) => [index("posts_author_id_idx").on(table.authorId), searchIndex(table)],
export const postFactory = defineFactory(postsTable);
await postFactory({ ...post, author: demo });
```
- `belongsTo(table, { column?, onDelete?, nullable? })` — every part
  overridable. The column type follows the target's `id`. It adds no
  index: a Drizzle column builder cannot add one, so the app keeps its
  `index(...)` line.
- Factories create a missing `belongsTo` parent from that table's factory;
  the relation name (`author`) comes from the column minus `Id`.
- `defineUserData(table)` reads the owner from `belongsTo(userTable)`.
- Hidden columns (`hidden()`, `allColumns()`, searchable vectors left out of
  `select()`) are dropped (YAGNI): no app has asked for them, and they
  would break every `select()` that reads such a column.

Decisions taken: `belongsTo()` adds no index, and hidden columns are
skipped.

Migrations: `belongsTo` must generate the same SQL as the hand-written
form, proven by a `db:generate` test on a scratch app (no migration for
apps that switch).

## Milestone 10 — Realtime and jobs

- Channels send payloads with superjson (as tRPC does): `Date` survives,
  so `defineChannel({ events: { created: postSchema } })` and the client's
  `on.created` receive a typed `Post`. Breaking for code that read ISO
  strings → CHANGELOG step. Open tabs across a deploy reload through the
  existing build-ID check.
- `useJobChannel()` returns `status`, `progress`, `result`, `error` beside
  `events` and `close`.
- Omitted `authorize` on `defineUpload`, `defineChannel` and job `channel`
  means signed-in; `public: true` opens it. Additive (authorize is required
  today).
- `maxSize: "2 MB"` accepted beside bytes.

Decision taken: the client sends the build ID on the SSE connect, so the
reload check runs there.

Docs: `realtime.md`, `queues.md`, `storage.md`.

## Milestone 11 — Mail and notifications

```ts
// before
render: (props) => h(Welcome, props),
toDatabase: ({ name }) => ({ title: `Welcome, ${name}`, body: "...", url: "/profile" }),
toPush:     ({ name }) => ({ title: `Welcome, ${name}`, body: "...", url: "/profile" }),
// after
template: "Welcome",
message: ({ name }) => ({ title: `Welcome, ${name}`, body: "...", url: "/profile" }),
mail: $mails.welcome,
```
- `defineMail({ template })` resolves `server/mail/templates/<name>.vue`,
  props checked against `input`; `render` stays for custom rendering;
  `preview` defaults to `sampleInput(input)`.
- `defineNotification({ message })` feeds database, push and the mail's
  data; `toDatabase` / `toPush` / `toMail` override per channel.

## Milestone 12 — Pages and routes

- Route groups: `pages/(app)/...` and `pages/(guest)/...` get their meta
  from `nuxvel.pages.groups` (default
  `{ app: { middleware: "auth", layout: "app" }, guest: { middleware: "guest", layout: "auth" } }`).
  The map is configurable; `definePageMeta` in a page wins. Template moves
  its pages into groups (new apps only; existing apps keep working).
- `useRouteInput({ query?, params? })` — parses `route.query` / `route.params`
  with a schema, reactive, falls back to the schema's defaults. Named to
  avoid VueUse's `useRouteQuery`/`useRouteParams`.

## Milestone 13 — Auth composables

Each wraps Better Auth's `{ data, error }` into a reactive mutation shape
(same as `$api.x.useMutation()`), with translated fallback messages:

- `useSessions()` — `list`, `revoke(token)`, `revokeOthers()`
- `useChangeEmail()` — `mutate(newEmail)`, `requested`
- `useTwoFactor()` — `enable(password)` (returns `totpURI`), `verify(code)`,
  `disable(password)`, `backupCodes`
- `useResendVerification(email)`
- `unwrapAuth(result)` exported for any other Better Auth call.

`playground/app/pages/security.vue` script: ~60 → ~10 lines. `AuthForm`
uses them internally. `authClient` stays fully available.

Docs: `auth.md`.

## Release checklist

- Each milestone is a series of one-change commits, each with its test,
  TSDoc, `docs/` update and `CHANGELOG.md` line (breaking ones with steps
  and the codemod name).
- Type probes for every new public type (`IsAny<T> extends true ? never : true`).
- Playground and template rewritten to the new style; `create.test.ts`
  typechecks the new starter.
- `nuxvel upgrade` run against a copy of the 0.2.0 starter and the
  playground at the 0.2.0 tag: the result typechecks and its tests pass.
- `npm run test:release` before tagging; release commit renames
  `## Unreleased` to `## 0.3.0`.

## Order

0 → 1 → 2 → 3 → 4 → 5 → 6 → 7, then 8–13 in any order (independent),
then 14 after 13.
Milestones 2–7 depend on each other; 8–13 do not depend on forms.
